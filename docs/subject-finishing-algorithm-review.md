# Subject finishing: algorithms, colour and pipeline review

Research date: 10 October 2026, Australia/Sydney. Scope: optional sharpening and colour/light for the selected horse and rider, protection of optical background bokeh, CPU/GPU throughput, compatibility with the existing stabilization and fragment cache. This report records source review and engineering recommendations. No footage was inspected, no model was downloaded, no dependency was installed, and no benchmark, build or release was run for this review. Upstream benchmark results below are the authors' measurements, not PhotoGoGo measurements.

## Blue-team verdict

- **Upside:** a restrained, temporally stable subject treatment can improve the perceived definition of tack, coat, mane and rider while retaining the 400 mm f/2.8 photographic separation. Masking is materially useful because a spatial sharpener cannot distinguish intentional optical blur from unwanted softness by itself.
- **Downside:** mask mistakes, sharpening stencils crossing the silhouette, repeated lossy encoding, sensor noise and changing masks can make the result less natural. Existing Quality bases already contain global sharpening. Current output normalization also reduces pictures to 8-bit H.264/YUV420P before later finishing.
- **Verdict:** proceed with a conservative spatial luma treatment and fixed shot-level colour settings. Treat generative restoration and blind deconvolution as separate experiments. Introduce an explicit new clean-base profile without deleting or reinterpreting legacy caches.
- **Alternatives:** FFmpeg luma unsharp plus a protected mask is the smallest measurable baseline. A native CPU filter can enforce stencil safety more directly. A compact native GPU adapter is a sensible later comparison when upload/download costs are included.
- **Next step:** use synthetic fixtures and an authorized short horse/rider sample to compare the same mask with luma unsharp and RCAS, including real-time playback, boundary crops, colour charts and end-to-end render timings. Select defaults from that comparison; do not publish a generic speed multiplier.

### Legacy background preservation needs precise wording

Two promises must be distinguished. A subject finishing pass can leave pixels outside its effective mask unchanged **relative to its input base**. It cannot undo sharpening, scaling, colour conversion or compression already baked into that base. It cannot reconstruct the original optical blur from a legacy Quality cache.

Recommended compatibility policy:

1. Keep legacy base keys and files valid. Disabled finishing continues the old render path exactly.
2. Version a new clean-base profile that preserves the same stabilization analysis/path/interpolation/framing but omits global unsharp. Use that profile when preparing new clips for strict subject-only finishing.
3. Reusing an old base is valid, with provenance showing that the base contains legacy global sharpening. Reduce additional subject gain until previewed. Do not label its background as original-camera bokeh.
4. Offer explicit regeneration from source into the new clean profile when strict preservation is wanted. Do not silently purge or regenerate all bases.
5. If reusable motion-transform data is available, reuse it under its own verified identity; current base MP4 reuse alone is not proof that a transform cache exists.

| Candidate | What the primary source establishes | Assessment for this footage |

| Luma unsharp | FFmpeg exposes independent luma/chroma/alpha treatment and convolution-based sharpening. The reference accepts EASU's display-like RGB output. [RCAS source](https://github.com/GPUOpen-Effects/FidelityFX-FSR/blob/master/ffx-fsr/ffx_fsr1.h). | Strong second candidate after output scaling and colour normalization, before graphics. | Edge-aware multiscale/detail enhancement | Local Laplacian filters distinguish large edges from small detail and manipulate a pyramid. Published example code is not an assumed redistribution licence; verify the chosen implementation. |
| Wiener deconvolution | Requires a point-spread function and regularization balancing restored frequencies against noise artifacts. [Maintainer documentation](https://scikit-image.org/docs/stable/api/skimage.restoration.html#skimage.restoration.wiener). | Separate expert experiment with an estimated blur kernel. A single PSF is a weak assumption for camera pan plus moving legs, mane and rider. Kernel error can create ringing/double edges. |
| Richardson-Lucy | Requires a PSF; iteration count acts as regularization. The implementation also has explicit clipping and small-denominator behaviour. [Maintainer documentation](https://scikit-image.org/docs/stable/api/skimage.restoration.html#skimage.restoration.richardson_lucy). | Avoid as a default. Iterative cost and temporal changes in PSF/iterations need extra control. More iterations are not a universal quality improvement. Do not confuse this with an ordinary sharpness slider. |

These spatial methods change contrast around evidence already present; they do not establish recovery of information removed by motion blur. Raising gain on a moving hoof can emphasize both blurred edges. A useful preview must include gallop/jump motion, not just a paused frame that looks sharper. These are engineering conclusions from the filter mechanisms, not claims that an authorized sample has passed.

## Recommended masked treatment

This section is a proposed implementation, not shipped behaviour.

Let `I` be the decoded clean picture, `T(I)` a pointwise colour treatment and `S(I)` a sharpened candidate. Use independent effective weights for colour and sharpness:

```text
J = I + colour_weight * (T(I) - I)
O = J + sharp_weight  * (S(J) - J)
```

An effective weight of zero must take an explicit copy/bypass path. That makes the pre-encode outside-mask invariant testable and prevents a nominally disabled stage from imposing a colour round trip. Encode error is a separate layer; output bitstreams cannot be expected to preserve outside pixels exactly after lossy re-encoding.

A binary segmentation silhouette followed by a blur is insufficient protection. Filtering an opaque boundary pixel can read background neighbours and place a bright/dark contour on the subject even if the final blend never writes outside the silhouette. Recommended protections:

- Build a trusted interior from confidence and distance to the uncertain silhouette. Require the **whole sharpening footprint**, including the blur used by unsharp, to be trusted. Erode by that footprint's support or use a minimum-confidence stencil gate.
- Preserve a protection fringe around mane, tail, reins, ears and helmet. Thin structures may receive less sharpening; that is preferable to a moving halo. Grow the fringe with uncertain motion/low resolution rather than using a fixed screen-independent width.
- For a native blur, use positive mask-aware weights with explicit normalization and a guarded denominator. Do not replace out-of-mask samples with black. Where the stencil is incomplete, reduce sharpness toward zero rather than inventing a boundary continuation.
- Apply a soft inward blend between protected fringe and trusted core. Confidence estimates need calibration on the target clips; an arbitrary probability threshold is not proven certainty.
- Pointwise colour can use a slightly broader soft weight than sharpening because it has no neighbour stencil. Small exposure changes still need a restrained transition to avoid an artificial cutout.
- Resize probability masks with a bounded nonnegative interpolation rule and clamp to `[0,1]`. Higher-order interpolation can overshoot; it is not automatically a better confidence mask.
- Advect temporal mask history into the current picture coordinates before smoothing. Raw same-pixel averaging trails moving limbs. Reset history at cuts, occlusion, lost identity, resolution/timebase changes and confidence failures. A failed mask should fade/bypass treatment, never silently become a full-frame mask.

Global stabilization and subject-mask stabilization solve different problems. Keep the existing camera path; align masks to the picture after the applied stabilization/scale/crop. If masks are analyzed earlier, save and apply the identical geometric mapping. Carry PTS and source-frame identity so VFR/B-frame input, fps normalization and replays cannot shift a mask by one frame. Motion blur/noise confidence should reduce local sharpness; it should not trigger a stronger rescue preset.

## Colour and bit-depth contract

Do not infer recording mode from the Canon brand, codec name alone, or a file extension. Probe transfer, primaries, matrix, range, pixel format, chroma location and bit depth; retain a manual profile override when tags are missing or unreliable. [BT.709](https://www.itu.int/rec/R-REC-BT.709) and [BT.2100](https://www.itu.int/rec/R-REC-BT.2100) are distinct signal definitions. A range tag changes interpretation, not sample values.

| Input | Required treatment |
| --- | --- |
| Confirmed 8-bit Rec.709 SDR | Respect full/limited sample range and matrix. Keep higher precision during processing; deliberately quantize/dither at the output. An 8-bit source does not gain captured dynamic range by being stored as float. |
| 10-bit Canon Log 3 | Preserve precision before the first SDR cache. Use the exact Log curve **and recorded gamut** transform, not generic gamma or a LUT selected by filename guess. Canon provides linear/BT.709/PQ conversions and 3D LUTs including gamut conversion in its [Log white paper](https://www.usa.canon.com/content/dam/canon-assets/white-papers/pro/white-paper-canon-log-gamma-curves.pdf). Verify redistribution rights if bundling Canon LUT files. |
| HDR PQ / BT.2020 | Interpret PQ's transfer and luminance deliberately. For SDR delivery, tone-map and gamut-map before reducing precision, and label the output Rec.709. For HDR delivery, preserve suitable 10-bit output and consistent metadata throughout. Never retag PQ pixels as SDR. |
| Unknown/mixed profiles | Request an explicit profile or reject the colour treatment with a readable explanation. Do not normalize all Canon clips through the same assumed matrix/transfer. |

Proposed ordering: decode/high precision -> input colour normalization -> existing geometric stabilization/resize -> shot-level subject colour/light -> final-resolution conservative sharpness -> titles/scorecards -> output transform/range/chroma quantization -> encode. Where the chosen sharpener requires normalized display-like samples, give it that documented domain; where a colour operation is labelled exposure in EV, perform gain in the appropriate linear-light representation. Scene-referred camera OETF and display EOTF are not interchangeable assumptions. Validate the selected contract with known patches.

For a first SDR release, restrict the supported colour contract explicitly rather than claiming automatic Log/HDR preservation. Adding float calculations after an 8-bit base cannot recover information already discarded. A complete 10-bit path changes base format, encoders, validation, cache identity, graphics/replay formats and preview colour management; treat it as a distinct profile.

There is a further geometric-stage constraint: the current upstream [FFmpeg vid.stab format table](https://github.com/FFmpeg/FFmpeg/blob/master/libavfilter/vidstabutils.c) advertises only 8-bit YUV/GRAY/RGB24/RGBA formats. Merely selecting HEVC Main10 at the encoder does not preserve 10-bit input through `vidstabtransform`. A full high-precision path needs verified high-precision geometric application of the same camera transforms, or an explicit SDR conversion before this stage. Preserve stabilization equivalence as a separate gate; do not silently replace the interpolation/path algorithm to obtain higher precision.

Use one fixed grade per shot by default. Auto recommendations can be derived from robust subject statistics over a shot, but a black horse is not underexposed because it is dark, and a white coat/specular bridle highlight should not dictate exposure. Keep neutral coat/skin hues, smooth highlight roll-off and bounded saturation/gamut behaviour. Avoid separate per-channel hard clips. Per-frame auto exposure or histogram equalization is a poor default because mask coverage and changing scenery can pump the image. If illumination genuinely changes, use a slow bounded parameter curve with scene resets and show it in the preview.

Disabled colour and disabled sharpening must preserve the existing baseline recipe and cache identity. Zero EV/neutral parameters must be identity through the module interface. A mandatory input/output colour conversion for a chosen delivery format is separate from the creative treatment and must be reported as such.

| Native wgpu compute | A compact shader can support Intel/NVIDIA/AMD through [native DX12/Vulkan backends](https://wgpu.rs/doc/wgpu/enum.Backend.html). wgpu is [MIT/Apache-2.0](https://github.com/gfx-rs/wgpu). | New dependency, adapter discovery, format/feature/limit negotiation, shader validation and device-loss recovery. Existing CUDA-only code does not become XPU-compatible automatically. Native Windows tests are still required; WSL results do not validate a packaged Windows worker. |

wgpu does not automatically import FFmpeg GPU frames. Its [device documentation](https://wgpu.rs/doc/wgpu/struct.Device.html#method.create_texture_from_hal) makes low-level texture import unsafe and backend-specific, requiring the resource to originate from that device's internal handle with matching descriptor/state. External plane textures likewise must already exist as wgpu textures. Treat decode -> CPU stabilization -> upload -> finish -> download -> encode as a real candidate path and include both copies in timing. A claimed zero-copy path needs a demonstrated compatible device, resource lifetime and fence/state ownership.

The official [NVIDIA codec matrix](https://developer.nvidia.com/video-encode-decode-support-matrix) supports H.264 and HEVC encoding, including HEVC 10-bit, on the RTX 2060 family; AV1 and HEVC 4:2:2 encoding are not listed as supported. Turing decode tables also do not provide HEVC 4:2:2. This matters for Canon 10-bit 4:2:2 sources: retain CPU decode fallback and probe the actual stream/runtime. An encoder listing or marketing specification is not an execution test. Intel Arc capabilities depend on the actual adapter and stream and need their own validation.

### Keep the whole pipeline bounded

The performance objective is completed, validated output per wall-clock second at unchanged quality, with bounded host/VRAM use. Reuse masks and grades; detect/analyze at an appropriate lower resolution, propagate where reliable, and sharpen at final output resolution. Measure false mask decisions as well as inference time. Cropped subject processing can save filter work, but must include kernel padding and moving ROI alignment.

Use fixed small buffer pools and bounded queues. Do not store all 4K frames or masks in RAM. For reference, a 3840x2160 RGBA16F frame contains about 63.3 MiB of pixel data; a float32 RGBA frame about 126.6 MiB, before allocator/decoder/model overhead. Queue size is a budget decision, not an arbitrary large batch. Align job admission with the existing rendering resource policy so segmentation, native compute and the parallel stabilizer do not each independently saturate the machine.

Fold colour, sharpening and blend into one finishing pass. The current architecture already stores lossy H.264 bases and may encode title/replay/scorecard fragments again. Therefore **one additional finishing encode** is a credible scoped target; **one lossy encode for the entire existing workflow** is not currently established. A literal single final lossy encode needs source-plus-transform reuse or lossless/high-bit-depth intermediates and a larger cache/storage/assembly design.

Place a deep finishing module at the clean-picture seam. Its interface should accept an immutable recipe, typed colour contract, aligned mask input, selected execution adapter, cancellation and resource budget; it should return the output plus provenance/coverage/timing. Hide stencil gating, transfer handling, buffer ownership and backend fallback inside its implementation. Keep only adapters that actually vary, such as CPU and tested GPU; avoid a broad hypothetical plugin framework.

Cache separate identities for input base/profile, mask analysis (source/timebase/geometry/subject/model/weights/version), grade, finished picture and downstream graphics/replays. Colour/sharpness tuning should not repeat camera-path analysis. An algorithm/model/profile/version change must not silently reuse incompatible output. Save failure status and provenance without logging full private media paths unnecessarily. Publish only a verified completed file; cancellation, GPU loss or malformed masks leave the existing cache/export recoverable.

A whole assembled-video import is a separate supported input mode: baked text/cards are already pixels. Without supplied graphics exclusion masks or reliable source metadata, the pipeline cannot promise to preserve them. Prefer clean pictures, finish once, then derive replays and composite all graphics. Standalone title cards must bypass subject finishing; overlays must be composited after it.

## Validation and release gates

These are proposed acceptance tests, not results obtained in this research task.

1. **Disabled identity:** old projects missing new fields deserialize to the existing baseline. Filters, cache keys and decoded output are unchanged with finishing disabled. Zero creative settings and empty/zero masks copy exact pixels before encode.
2. **Stencil/bokeh protection:** synthetic sharp foreground over smooth bokeh and bright/dark silhouettes; compare every outside-mask pre-encode sample. Include thin hair/reins, partially transparent edges, borders and motion. Check inside-boundary halos as well as outside writes.
3. **Temporal fidelity:** cuts, fast limbs, occlusions, two horses crossing, subject exit/re-entry, dropped/duplicate frames, VFR and B-frames. Inspect original-speed playback and replays for flicker, trailing masks and double edges. Reset history deterministically; never borrow a mask from another clip.
4. **Noise/blur:** uniform noisy patches, gradients and known motion-blur fixtures. Measure noise amplification and edge overshoot; inspect fur texture for plasticity or false texture. A sharper metric alone is insufficient.
5. **Colour:** known Rec.709 full/limited charts and 10-bit Log/PQ ramps where supported. Verify matrix/transfer/gamut/range/chroma tags and decoded samples; detect banding/clipping and neutral hue drift. Unsupported profiles fail clearly before producing a misleading output.
6. **CPU/GPU parity:** same immutable recipe/mask/colour contract, odd dimensions, padding, differing row strides and tile seams. Establish justified numeric tolerance for floating point and exact bypass. No in-place stencil race; source buffers remain intact.
7. **Cache/order:** retune grade/sharpness, edit title/scorecard, add replay, reorder clips and reopen projects. Correct artifacts invalidate; verified camera stabilization remains reusable. Titles/cards and audio are unchanged by image treatment.
8. **Resilience/security:** nonfinite parameters, oversized mask dimensions, malformed worker output, stale PTS, missing weights, failed adapter, out-of-memory, cancellation and device loss. Validate inputs at the native seam; pass process arguments structurally, enforce model hashes/owned paths and bounded queues. No dynamic code/model download in a render job.
9. **End-to-end performance:** fixed source/recipe/quality, warm and cold caches, authorized Intel Arc and RTX 2060 tests. Report decode, stabilization, mask inference, copies, colour/sharpness, graphics, encode and publication time, completed frames, CPU/VRAM/RAM peaks and queue waits. Include concurrent-job behaviour. Native/shader-only FPS is supplementary evidence.
10. **Packaging:** native Windows clean-machine runtime closure, licences/notices/exact sources, binary/model hashes, optional runtime-off fallback, installer extraction and rollback. The [FFmpeg legal page](https://ffmpeg.org/legal.html) states that enabling optional GPL parts makes GPL apply to that FFmpeg build; inspect the exact configured binary and preserve its corresponding source obligations. AMD MIT shader notices must accompany copied code. Do not assume a permissively licensed sharpener changes the existing media backend's licence.

The parallel stabilizer fork should retain its own byte-equivalence and temporal-path tests before integration. Re-run the relevant complete Quality pipeline after combining changes. Do not attribute a whole-render improvement to row parallelism, subject finishing or GPU execution without separately measured stages. Stop release progression if background protection, temporal alignment, colour identity, cache compatibility, media verification or resource limits fail; do not compensate by quietly reducing stabilization or encoding quality.

Filtergraph ownership also matters: the current upstream [vidstabtransform wrapper](https://github.com/FFmpeg/FFmpeg/blob/master/libavfilter/vf_vidstabtransform.c) requests writable input because alternating separate-buffer and in-place library paths can leave a stale source pointer. Introducing split/merge branches can change writability. Preserve the fork's ownership correction and test alternating/in-place/out-of-place buffers; do not assume a branch that only changes sharpening cannot affect stabilization memory safety.

## Follow-up: minimal CPU / D3D11 reference sharpener

This is an explicit proposed algorithm and acceptance contract for implementation. It is **not RCAS**, deconvolution or detail reconstruction. The arithmetic examples below were evaluated from these equations in an isolated calculation; no application worker, GPU, media or benchmark was executed. The inspected report worktree did not yet contain a finishing worker implementation, so the frame interface below is proposed rather than an assertion about an existing function.

### Accepted SDR contract and proposed limits

The clean reference input is confirmed 8-bit, limited-range Rec.709 Y-prime with aligned treatment-mask bytes. Its nominal luma interval is 16 through 235; Cb/Cr and metadata pass through unchanged. This is perceptual luma-domain sharpening, not linear-light exposure correction. [BT.709](https://www.itu.int/rec/R-REC-BT.709) defines the signal representation; colour normalization belongs upstream. An unknown transfer/matrix/range, Log/PQ, interlaced input or a higher bit depth is outside this recipe and must not be silently reinterpreted. Recipe version: proposed `limited709-y8-q4-v1`.

| Parameter or property | Accepted limit |
| --- | --- |
| Gain `G` | Integer 0..128 in Q8; default 64, giving a nominal gain of 0.25 and maximum of 0.5. Zero bypasses the stage. |
| Noise floor `sigma16` | Integer 0..128 in Q4 luma-code units; default 16, meaning one luma code. The recipe uses `T16=max(32,2*sigma16)`, so the minimum soft threshold is two codes. This supplied floor is not a calibrated noise estimate. Keep it fixed per shot; automatic estimation requires separate evidence. |
| Trusted-mask threshold | Minimum of all nine mask samples must exceed 240. Effective inward alpha is `(minimum-240)*17`, giving 0..255. The threshold is a conservative numerical policy, not proof that model scores are calibrated. |
| Support | Exact 3x3 source stencil, radius one. Missing full support copies the source pixel. A separate mask-refinement radius must already be reflected in the supplied mask. |
| Change bound | Gain-adjusted residual is capped at plus/minus three luma codes **before** range and alpha blending. Final output differs from source by at most three codes. |
| Local bound | Final luma lies within the minimum and maximum of that pixel's original 3x3 stencil. No value outside the original local interval can be introduced. |
| Range excursions | If any of the nine source samples is outside nominal 16..235, copy the centre. Preserve excursions; do not clip them merely to satisfy this sharpener. Source bytes themselves must be 0..255. |
| Chroma and padding | Copy unchanged. All output comparisons are pre-encode. Lossy encoding has a separate error contract. |

These numerical limits are proposed release criteria, not parameters validated on horse footage. They can be deliberately changed after preview evidence, with a new recipe identity. A conservative default may correctly make no visible change to already-sharp footage.

### Exact integer equations

Reject invalid frame/mask identity, geometry, stride or colour contracts before processing. Read every stencil sample from an immutable source frame. Let the centre be `Y`, local bounds `L=min(N)` and `H=max(N)`, and minimum treatment weight `m=min(M(N))`. Initialize the destination centre by copying the source. If gain is zero, the stencil is incomplete, `m<=240` or a nominal-range excursion is present, retain that copy.

Use Gaussian weights whose sum is 16:

```text
1 2 1
2 4 2
1 2 1
```

The proposed calculations are:

```text
W   = sum(weight_i * Y_i)                 // 0..4080 for arbitrary valid bytes
D16 = 16*Y - W                           // signed high-frequency residual
T16 = max(32, 2*sigma16)
S16 = sign(D16) * max(abs(D16)-T16, 0)   // soft threshold / noise rejection
K16 = clamp(roundDiv(S16*G, 256), -48, 48)
R   = H-L
Q   = clamp((R-4)*32, 0, 256)            // zero at range <=4; full at >=12
A   = (m-240)*17                         // only evaluated when m>240
V16 = roundDiv(K16*Q, 256)
U16 = roundDiv(V16*A, 255)
d   = roundDiv(U16, 16)
O   = clamp(Y+d, L, H)
```

Define `roundDiv(v,n)` identically on both adapters, with positive `n`:

```text
v >= 0 : (v + floor(n/2)) / n
v <  0 : -((-v + floor(n/2)) / n)
```

Here division is integer truncation toward zero, equivalent to floor on the nonnegative numerator used in each branch. This gives symmetric nearest rounding, with half ties away from zero. Use signed 32-bit integers for the equations and validate parameters before dispatch. Staged divisions keep the intermediates comfortably within signed 32-bit bounds; a single combined product is unnecessary and can overflow. Do not substitute floating point, GPU `round`, normalized texture sampling, a fused expression or a different division order in the parity implementation.

Cap `K16` before alpha multiplication. If a large residual were capped only after blending, the first small nonzero fringe alpha could still produce the full three-code change. This order ensures the blend attenuates an already bounded correction.

The threshold rejects all residuals at or below `T16`. The range gate additionally makes every stencil with range four codes or less exactly unchanged, including flat regions containing bounded plus/minus-two-code noise. Neither rule identifies all sensor or compression noise. A high-contrast noise pattern can pass both rules if the supplied floor is too low; randomized noisy fixtures must therefore be part of acceptance.

For fixed source, mask and noise floor, increasing gain can only increase the magnitude of the correction toward its bound; its sign cannot reverse. The output remains within `L..H`. This is the accepted **monotonic strength and local-bounds** promise. It is not a claim that the operator is order-preserving with respect to arbitrary changes in neighbouring input samples, or that it cannot create a local extremum relative to neighbouring *output* samples. A negative-lobe sharpener does not generally provide those stronger properties.

### D3D11 representation and RGB-worker variant

Use separate immutable SRV input and UAV destination resources, with one invocation owning each destination pixel. No in-place source/output aliasing or per-pixel shared packed-word writes. A straightforward parity proof can use `R32_UINT` textures containing integer Y/mask samples and `RWTexture2D<uint>` output; probe the required format support and feature level. Microsoft's [Shader Model 5 RWTexture2D documentation](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/sm5-object-rwtexture2d) and [typed UAV specification](https://microsoft.github.io/DirectX-Specs/d3d/UAVTypedLoad.html) establish the relevant resource rules. Reading SRV inputs and writing a separate UAV avoids relying on optional narrow-format UAV loads. Source/output bindings must be released appropriately before copies or reuse. Device errors return a controlled failure or selected CPU fallback, never uninitialized pixels.

For a worker that publicly accepts full-range opaque BGRA/RGBA bytes, use a separately versioned recipe rather than pretending the limited-Y recipe applies unchanged. A minimal proposed `sdr709-rgb8-q4-v1` variant:

- Require known Rec.709 **encoded** RGB with full 0..255 sample range. Compute integer perceptual luma `Y=(54*R+183*G+19*B+128)/256`; the coefficients sum to 256 and approximate Rec.709 luma weights. This is not an sRGB/709 conversion, and must not be applied to unspecified web-image colour.
- Apply the same residual/threshold/gain/range/mask equations to that luma, using `0..255` as the nominal interval. Keep the same three-code cap, which is slightly more conservative relative to the full RGB scale. Record this variant in the recipe identity.
- Restrict the common signed change to `max(L-Y, -min(R,G,B)) .. min(H-Y, 255-max(R,G,B))`, then add **the identical integer change** to R, G and B. This avoids independently clipping channels. The luma then shifts by exactly that integer change and encoded channel differences stay unchanged. Copy alpha. If the source stencil is not opaque, bypass until its premultiplication/alpha contract is explicitly supported.
- Pack original byte data into an explicitly created integer resource if desired. Do not reinterpret an arbitrary existing BGRA GPU texture as an `R32_UINT` view or claim interoperability without a compatible resource contract. Integer texture loads require no sampler and must not invoke sRGB decoding.

This RGB variant is testable but does not establish byte equivalence to decoding a YUV frame, sharpening Y and converting back. That conversion has its own rounding/chroma semantics. CPU and D3D11 must compare the **same public variant**. An outside-mask copy preserves all original BGRA bytes exactly, including colours near channel limits; it must not take an RGB/YUV round trip.

### Public frame / worker acceptance tests

The proposed test surface is a public typed frame request: dimensions, validated row strides and plane/packed format, bytes, colour contract, PTS/frame identity, aligned mask bytes, immutable recipe and requested CPU/D3D11 adapter. The worker returns a same-layout frame plus adapter/recipe provenance or a typed error. A media test uses the real worker on a short synthetic clip and reads back decoded output; private implementation helpers are not the only test surface. Dimension/stride products use checked arithmetic, limits apply before allocation, and frame/mask PTS or geometry mismatches reject the request.

Use generated public fixtures with known ground truth; external footage downloads are unnecessary. Include:

1. **Exact identity:** constant legal luma, gain zero, empty mask, every mask value 0..240, one-pixel borders, 1x1/2x2/small odd geometry, nominal-range excursions and unchanged Cb/Cr/alpha/padding. Require byte equality and unchanged source buffers.
2. **Useful sharpening with known numbers:** repeat columns `[64,64,80,112,160,192,208]` vertically, trusted full mask, default recipe. Interior-row output is `[64,64,79,111,161,193,208]`; outer frame rows copy. This exercises both signs and rounding, rather than accepting an accidental all-bypass implementation.
3. **No halo beyond local source bounds:** a hard step 64 to 192 retains the two boundary values 64 and 192; isolated extrema and checkerboards stay inside every original local interval. Assert `L<=O<=H`, `abs(O-Y)<=3`, and correction sign equals residual sign or zero for every pixel.
4. **Noise gate:** every stencil with range <=4 is exactly unchanged. Bounded six-code noise around a flat patch with `sigma16=96` has range <=12 and residual <=12 codes, so its threshold rejects it exactly. Also use seeded Gaussian/impulse/compression-like noise, both flat and on fur-like detail. Proposed statistical gate: corrected flat-patch standard deviation must not exceed 1.03 times input; any exception requires tuning or bypass, not a claim the proxy has detected noise correctly.
5. **Mask support/fringe:** move a known foreground silhouette across a smooth background. A zero or <=240 sample anywhere in a sharpening footprint copies its centre exactly, including opaque centres next to uncertain edges. Sweep a uniform mask from 240 to 255 on `[64,160,208]` with maximum gain: the centre sequence is `[160,160,160,161,161,161,161,161,162,162,162,162,162,163,163,163]`. Verify inward attenuation and byte-identical outside pixels.
6. **Monotonic gain and symmetry:** sweep every integer gain 0..128 at fixed source/mask/noise. Correction magnitude never decreases or reverses sign. Mirror/rotate stencils and reflect values about a legal midpoint; corresponding output symmetry must hold away from copied frame borders.
7. **Temporal sanity through the worker:** repeated identical frames produce identical output; adding one code to an entire legal frame shifts the output by one code where range guards remain unchanged. Translate frame and ground-truth mask by integer pixels: interior output translates identically. Misaligned PTS, cuts/resets and frame-size changes reject or reset according to the public temporal contract. These tests do not prove fractional-motion mask stability; preview that separately.
8. **Adapter parity and memory safety:** every output byte matches CPU on the same fixtures and seeded random frames across Intel and NVIDIA adapters, including padded strides, non-workgroup-sized dimensions and repeated/cancelled jobs. Check output initialization, input immutability, checked bounds and proper readback completion. A D3D11 result that differs by even one byte is a failed parity result for this integer reference; report and fix it before broadening performance work.
9. **RGB-specific checks where used:** saturated red/blue, black/white, skin/fur-like colours and transparent input. All channels receive the same change within shared headroom; alpha and all bypass pixels remain exact. Reject unknown colour/premultiplication contracts. Compare CPU/GPU before media encoding; encoded output is assessed separately.

Fail the quality gate on any outside-mask write, source-buffer mutation, illegal local overshoot, correction >3 codes, CPU/GPU mismatch, invalid-frame acceptance, accidental all-bypass on the useful fixture or measured flat-noise amplification above the proposed limit. Keep mathematical invariants fixed while comparing quality presets; do not loosen parity or bokeh protection to obtain a performance win. Horse/rider footage still needs authorized real-time visual review before these synthetic gates justify release.

Keep the current `studio_start_render`/`render` export preflight unchanged.

**Exact-source and colour gates.** Reuse `source(:520)`, source inspection and `stabilization::base_key/quality_filter`, `output_video_filter(:1769)`, `encoder(:1481)`, `gpu_tripod::render_base(:64)` and `run(:1224)` for the rendering recipe, without cloning a second stabilizer. Source containment is not an immutable lease; `source_signature(:1575)` also hashes without cancellation or a lease. Use the finishing cache's opened-object reparse check, ancestor guards and `hashes(...,Some(id))` around this workflow, retaining the existing legacy source-key fields. Require explicit SDR7098 source admission or a separately approved conversion; the current generic output filter/encoder establish limited yuv420p, not a proven HDR/Log-to-SDR conversion or a complete BT.709/progressive contract. `gpu_tripod::validate_source` accepts some unknown tags, so it is not the strict subject eligibility check. Reuse `cache::validate_profile(:206)` plus `verify_output(:1743)` on the leased actual normalized base; parse its measured positive bounded `nb_frames` rather than accepting UI count or rounding source duration. Unknown tags and unsupported profiles must fail closed, not be relabelled.

**Cache and path caveats.** `cached_video_is_valid(:1604)` checks the weak legacy sidecar/length/geometry/audio/duration; `publish_fragment(:1688)` can delete invalid existing entries and has no post-verification cancellation check. Keep those legacy semantics unchanged for disabled finishing, but do not use them as stronger source-provenance or no-replace publication evidence for the new public workflow. An eligible legacy candidate can be explicitly adopted/reviewed as the actual measured bytes; that does not retrospectively prove its original generation. Guard/open the actual lock without following reparse points before exposing the workflow. Choose app-generated cache/work names under a leased approved root; public commands accept a selected clip/preparation/job identity, never arbitrary cache/manifest/executable paths. All supplied source/output directories still need native validation.

**Cancellation/admission.** Reuse `checkpoint(:448)`, `stopped_or_paused(:1330)`, disk reservations (`:1444`), shared Studio/Tripod admission and `diagnostics::run_admitted_process(:59)` with `RETRY_ADMISSION`. Do not hold process/GPU permits while paused, acquiring another resource, hashing or waiting for user selection. The current generic `run` obtains its permit before `run_process`'s launch checkpoint; a queued pause in that interval can retain admission. Do not amplify that existing race with an outer preparation reservation. `inspect(:485)` is bounded to 30 seconds but has no job cancellation hook; if reused unchanged, document and test that cancellation latency and recheck before commitment/return. Publish a completed preparation result under the existing job cancellation protocol, never just after an unsynchronized final Boolean check.

**Selection/preview timing and read surface.** The native contract is integer frames of the full normalized base. Return and validate an index `0 <= n < N`; display `n/fps`, but do not accept arbitrary source seconds as proof of frame identity. Map mouse coordinates through the displayed proxy's actual content rectangle, including padding/letterboxing, back into normalized full-base coordinates. A display proxy may resize the already prepared base; it must not be separately stabilized, cropped, retimed or converted into the mask source. Current `studio_frame/frame_data(:748-780)` reads the original staging source by seconds and uses unbounded `Command::output` with no deadline; it is not a safe exact prepared-base frame reader. Reuse the bounded stdout/stderr-draining process helper (`process.rs:1170`) only with explicit limits/deadlines, ownership/admission and cancellation treatment. A public reader should resolve the saved preparation token, reacquire/verify its root/base lease and decode an exact frame. Bound concurrent frame requests and discard stale UI responses. `preview::owned_output/read` demonstrates job-owned fixed-name/checksum/bounded reads, but its preview-only semantics and 64 MiB inline limit must not be weakened to expose a long full-base file.

The simplest first finishing preview prepares/verifies the full base and full mask schedule, finishes that same picture through the existing worker, then trims/resizes only the displayed preview. Use exact full-base frame indices and include the preview range in derivative identity; do not feed an excerpt to masks starting at frame zero. Keep graphic/title/replay derivation separate. A faster interval-specific finishing worker would require a new explicit schedule/offset contract and tests; it is not a safe incidental optimization of this extraction.

## Smallest user-facing preparation interface and readiness state

**Current source clarification:** the finishing path now uses `cache::lock_owned`, which opens/checks the actual generated lock with Windows reparse protection and deny-write/delete sharing. The previously noted derived-lock problem is therefore fixed for this path; the legacy helper remains separate. `verified_masks` now requires `appCommitted`, the expected CPU runtime profile and the build-pinned runtime seal in addition to exact recipe/content checks. The runtime resolver refuses request-supplied executable/profile/hash authority and checks a sealed private pack before launch; it explicitly does not claim a same-user sandbox. These are static-source observations. No public preparation/selection commands or dedicated finishing panel were found in the inspected registration/UI snapshot.

**Verdict: proceed with a small purpose-specific interface; do not make existing movement preview the selection authority.** Reuse existing job status/progress/cancel machinery, but add narrowly admitted preparation/mask/subject-preview purposes rather than overloading `preview=true` or weakening export preflight. Suggested operations: prepare one selected clip's full normalized base; read an exact base frame with an optional verified mask overlay; prepare masks from that preparation and bounded selection; record explicit mask review; and start a bounded finishing preview from the reviewed identities/settings/range. Mutating operations return job IDs; public reads resolve native-owned preparation/artifact IDs, never arbitrary cache/executable paths. The preparation result carries base key/content identity, measured frame count/dimensions/fps/profile and the effective reuse/clean policy, including a legacy global-sharpening warning when applicable. Frame responses echo the preparation identity/index and display dimensions/content transform; preview responses echo base/mask/grade/range identity.

Keep durable evidence separate from transient jobs: base receipt, selection recipe, mask receipt, user review record and preview receipt. Derive readiness from exact identity equality rather than maintaining independent trusted booleans. The useful states are needs-base -> base-ready -> selection-ready -> masks-ready-unreviewed -> masks-reviewed -> preview-ready, with existing queued/running/paused/cancelled/failed job statuses attached to the active operation. A receipt is not ready until every required process and app verification/commit succeeds. Persist review separately from immutable generator manifests, binding it to base identity, canonical selection, mask identity/content hash and generation/runtime profile. Current worker `subjectQualityAccepted:false`, app commit success, an existing clip's `reviewed` flag and sample qualification are different facts; none implicitly accepts masks or lifts the export gate. State the user's review coverage, not a claim that every unseen frame is visually certified.

**Top three integration traps:**

1. **Wrong pixels or timing.** `StudioVideoPreview` describes its output as 720p and explicitly warns that full-pass stabilization may differ at preview edges. Its source-seconds callback is not subject-frame authority. Use integer full-base indices, exact frame reads and a declared resize/letterbox transform. Proxy sizing may change; full-base coordinates and mask schedule do not. Nonzero finishing-preview ranges trim only the same finished full-base picture; never restart masks at excerpt frame zero or restabilize that excerpt.
2. **Wrong dependency invalidation or cache policy.** Grade/sharpness changes invalidate only finishing preview/output. Prompt changes keep the base but stale masks/review/preview. Source/stabilization/framing/format/encoder/clean-policy changes require re-preparation and prevent old descendants from being represented as current; preserve them as stale evidence/cache, not deletion targets. After re-preparation, genuinely identical measured content/profile may be revalidated. Titles/replays do not affect this clean-picture selection/preview, though they still affect final clip/sequence readiness. Never disable finishing to bypass the gate, silently turn clean into reuse, or regenerate a missing clean base without the explicit user choice. Report the effective base policy and warning, including newly generated legacy Quality/reuse bases that still contain global unsharp.
3. **Premature or stale acceptance.** Generated masks remain unreviewed. A frontend success flag cannot authorize committed mask readiness or visual acceptance. Every request must bind to its native-owned preparation and exact recipe; late results can remain valid old cache artifacts but must not become the current panel state. Recipe/session identity must guard frame, overlay and preview responses. Cancellation, failure after a valid prefix and incomplete folders produce no accepted result. Read leases and validation bridge selection/preview requests; do not hold scarce GPU/process permits while waiting for user input.
