## User workflow

Copy/extract the entire ZIP to a short local folder on the render PC. Double-click `bin/PhotoGoGo-Cached-Picture-Test.exe`, choose a short ordinary local results parent, confirm other rendering is idle and select Run four tests. No test starts automatically. No Codex, development tools, installation, admin rights, driver change, reboot or policy change is required on that PC.

The sequence is black horse/mounted-rider CPU, black NVIDIA D3D11, white horse/handler NVIDIA D3D11, white CPU. These are two-second, 100-frame UHD50 bases with prepared masks. Each case uses a fresh owned process and independently validates its media and report. An unavailable NVIDIA adapter remains a failed case, never another-adapter/CPU success. Software libx264 encoding is deliberately fixed for this filtering comparison.

Return only the small `PhotoGoGo-Return-Reports.zip` to this Codex conversation. It includes aggregate and valid case reports plus their zero-byte hash-bearing markers; no media or private paths are included. On cancellation before bundling, the UI/README provides precise report-and-matching-marker-only fallback instructions. Never zip the full results folder, which contains videos. Unsigned/security-block warnings should be reported, not bypassed.

## Test-first corrections and bounds

Earlier failed candidates are retained, not replaced. Tests exposed source attribution gaps, ambient-job entry admission, startup termination without confirmed exit, a real junction staging hazard and a Windows rename failure under retained directory sharing leases. The report publication now writes/flushes/readbacks through a retained handle and creates a zero-byte hash-named marker using create-new under the cancellation mutex. The marker is the completion boundary; JSON alone is incomplete. Readers reject absent, nonzero, redirected, ambiguous or hash-mismatched markers and false identity/quality claims.

This marker design is no-replace controlled publication, not a tamper-proof signature, replay-protection system or multi-file power-loss transaction. The final ZIP is independently readable and has its own matching marker locally. The ZIP carries each diagnostic report's marker for return validation.

Each case has 90-second rendering and 180-second checkpoint deadlines, a 64 MiB output cap and 4 GiB owned-job committed-memory cap. Four cases run sequentially; the parent has a 760-second checkpoint deadline. Synchronous local IO can delay cancellation/checkpoints. The fixed 512 MiB free-space admission is conservative, not a measured minimum or a bound on other applications.

`filterAndTransferMs`, native pipeline time, render-owner wall and complete validation wall are separate observations. Peak memory means render-job committed bytes, not GPU VRAM, full-session memory or working set. One observation per case is not a statistical speedup claim. Cached masks exclude the substantial inference bottleneck.

No originals, app settings, stabilization caches, installed drivers or inference admission profiles were changed for this slice. The tiny shared ownership/adapter attribution changes retain legacy default behaviour. The main checkout was read only. No commit/merge/push, installer, Slack release or render-PC mutation occurred.
